FITS and XISF load benchmarks

The benchmark compares production AstroView APIs with independent readers:

Implementation Format Measured entry points
astroview-indexed FITS/XISF AstroFile.Open, selected HDU/image access, ReadPixels<T>
astroview-native FITS/XISF FitsReader.Load / XisfReader.Load, followed by ReadPixels<T>
astropy FITS astropy.io.fits.open, image arrays and owned native-endian copies
python-xisf XISF XISF(path), read_image(channels_first) and owned copies

Astropy and Python xisf are independent comparison implementations, not an official PixInsight certification or a claim that these are the fastest possible readers. Their versions are pinned in tools/interop/requirements.txt. They are development dependencies; the Core package does not depend on Python.

Optimized results: 2026-11-01

The current implementation removes per-element boxing and intermediate arrays from binary XISF matrices, takes internal ownership of newly decoded property values, scans matching floating-point pixels in vectors, and reads uncompressed attached XISF data directly into matching typed output arrays. Common exact type conversions use range and significant-bit checks instead of allocating rational values per pixel. The arbitrary scaling path, checksums, metadata and public ownership guarantees remain.

The optimized aggregate evidence uses exactly the same local and synthetic input bytes as the baseline below, with two warmups and seven measured iterations. Raw reports remain local alongside the baseline. The only pre-existing working-tree modification during measurement was documentation whitespace; the production implementation is committed and recorded in the evidence. Results are from an interactive machine and describe warm load latency.

Baseline results: 2026-11-01

These historical results predate the loading optimizations and are retained unchanged.

Measured on Windows with an AMD Ryzen 7 8840HS, 14.8 GB usable RAM, .NET 10.0.14 (workstation GC), Python 3.13.17, Astropy 8.0.2, Python xisf 0.9.7 and NumPy 2.5.4. This was an interactive development machine, with warmed caches and no CPU affinity. The aggregate JSON evidence records source revisions, policies, package versions, sizes, matched counts and results by sample type. Local raw reports retain every timing sample and fingerprint.

The local suite contains 84 files / 90 primary images / 6.14 GB of source data. The tables below separate the 11 large FITS files and 18 large XISF files from small controls. All comparable cases matched their pixels and masks. Four XISF files raised KeyError in the reference reader's pixel-loading path; those four are retained as failures and excluded from storage/pixel rankings. All AstroView cases loaded, and all 12 synthetic cases were independently verified.

On these large local images, native FITS storage loading was 1.47x faster than Astropy, while native XISF storage loading took 1.86x as long as Python xisf. Header discovery was faster in AstroView. These baseline gaps prompted profiling of numeric metadata, typed Float32 decoding and temporary buffers. The optimized results above retain the same workload and verification requirements. Both native and indexed APIs remain visible, including slower cases. No checksum, mask, supported type or precision policy was disabled.

What is timed

Headers measures fresh opening, discovery of every primary image and closing input handles. AstroView uses its metadata-only index. Astropy disables lazy HDU discovery, memory mapping and checksum reads. Python xisf's constructor also processes properties, which can include attached metadata. These are each reader's discovery workflows; they do not decode identical amounts of metadata. The eager native FITS API is deliberately absent from this comparison.

Storage isolates loading and decompression into reader-owned storage buffers that remain readable after closing the file. It retains file byte order and channel layout, with no typed-array normalization or missing-mask construction. FITS exposes retained HDU image payloads; XISF forces ReadRawData / read_image. A reference NumPy view may retain its reader-owned backing buffer in this stage; it is not a memory map or a lazy source. Every decoded storage byte and its geometry/type/layout/byte order are verified outside timing. This is the closest comparison to loading complete sample storage for later processing.

Pixels measures fresh opening and loading all primary images into owned, contiguous, native-endian, planar typed arrays, plus matching boolean masks. FITS uses stored values, retaining signed storage, unsigned-offset encodings and BLANK sentinels. Physical scaling is not part of this workload. XISF uses its native sample type. NaN is missing; infinity is not. Thumbnails, rendering, color transforms and saving are excluded. Complex32 expands to Complex64 for AstroView's shared API; unsupported reference types are reported explicitly.

In the Pixels workload, reference arrays are copied even if the reader returns a view. Merely opening a lazy document or a memory-mapped array cannot count as a full load. Headers are compared by geometry/type; typed pixels are compared by SHA-256 of all canonical little-endian planar samples and every mask byte, outside timing. Mismatches fail the run and never enter speed comparisons. The source files are hashed before/after their benchmark cases and are never edited.

Present FITS checksums are verified. The native AstroView FITS reader also materializes tables and checks all HDUs; the indexed path only materializes selected image HDUs. Astropy verifies all declared FITS checksums but does not decode all table cells. Files with substantial tables can therefore involve different work despite matching pixels. The local photographic FITS corpus is more representative of image loading than the tiny multi-table smoke fixture.

Forced collection outside the interval makes this an isolated load-latency benchmark. Runtime allocation/deallocation behavior still differs, and these numbers do not measure sustained throughput including all eventual cleanup.

XISF integrity work differs: AstroView verifies declared block digests, while Python xisf 0.9.7 does not. The report records declared image checksum algorithms. Byte hashing after timing validates comparison results but does not equalize the readers' timed integrity work. Treat the numbers as complete reader workflows, not isolated decompressor throughput.

Measurement policy

  • Each file/implementation/mode has its own sequential child process. No readers compete with one another for CPU or memory. Process startup, module imports, optimized JIT compilation, forced collection and result hashing are excluded.
  • Default: two untimed warmups and seven measured loads. Both runtimes collect outside each iteration. Collections that occur during a load remain timed. .NET tiered compilation is disabled so its warmup uses optimized code.
  • Files and implementation order are shuffled with a recorded fixed seed. Filesystem caches are warmed by the warmups; caches are not evicted. These are neither cold-disk nor first-application-launch measurements.
  • Raw milliseconds, median, minimum and interpolated p95 are retained. With seven samples, p95 is descriptive, not a confidence interval. System activity, filesystem, CPU, thermal state and runtime versions affect the results.
  • Summaries split small files from files at least 1 MiB and group by format, workload and codec. Ratios use the same successfully verified files for each implementation/reference pair. Each row states its matched-file count. Aggregate throughput divides source/decoded bytes by the sum of per-file median times. Source MiB/s for header discovery is not actual bytes-read throughput.
  • Errors, timeouts, unsupported formats and missing comparisons remain visible. Reference limitations are not patched or silently replaced with a custom decoder. --strict makes every failed/unpaired adapter a failure for CI's known-compatible fixture subset. Timing has no pass/fail threshold.

Run locally

Use .NET 10 and Python 3.13. From the repository root, install the pinned development packages into a dedicated environment:

python -m venv .local/benchmark-python
.local/benchmark-python/Scripts/python.exe -m pip install setuptools==84.2.1 wheel==0.48.0
.local/benchmark-python/Scripts/python.exe -m pip install --no-build-isolation -r tools/interop/requirements.txt
dotnet restore AstroView.sln --locked-mode
dotnet build tools/AstroView.Performance -c Release --no-restore
.local/benchmark-python/Scripts/python.exe tools/benchmarks/load.py `
  --directory C:\Code\AstroExamples `
  --astroview tools/AstroView.Performance/bin/Release/net10.0/AstroView.Performance.dll `
  --output artifacts/load-benchmarks/local-run `
  --warmups 2 --iterations 7

On Linux/macOS use python3 -m venv .local/benchmark-python, its bin/python executable, and ordinary shell line continuation. The benchmark CLI and worker are portable; timings must be measured on the platform of interest.

For a smaller run, repeat --include glob filters, e.g. --include 'libxisf/UInt16_Gray_*.xisf'. Use --modes storage for decoded storage loading, or --modes pixels for the additional typed-array/mask workload. By default all three stages run. --timeout caps each child process (180 seconds by default). Input files are discovered recursively by supported extensions and classified by content. Use a fresh output directory each time; measurements are never overwritten or mixed with previous runs. Large images require space for decoded storage, arrays and masks, potentially several times their on-disk size.

Reports and verification

The output directory contains:

  • report.json: settings, machine/runtime/package versions, source revision, input hashes, every raw iteration, full image/mask fingerprints and failures.
  • report.csv: per-file timing/status rows for spreadsheet analysis.
  • report.md: grouped comparisons and a failure table.
  • workers/: individual child-process results for diagnosing failures.

Local reports can contain file names and paths in error messages. They stay in ignored artifacts/; the photographs and their scientific metadata are not published. Published summaries contain aggregate measurements only.

CI builds the same Release worker, tests the report and canonicalization contracts, and runs a strict smoke comparison against independent FITS and XISF fixtures covering unsigned boundaries, cubes, multiple HDUs and every supported XISF codec. The file-load-benchmark-smoke artifact is diagnostic; CI runners are not stable performance baselines. This does not mark the unrelated allocation hotspots in roadmap AV-027 as complete.

The earlier median/MAD microbenchmark remains available through dotnet run --project tools/AstroView.Performance -c Release with no worker arguments.

Reproducible large compression cases

The current local photographs have large uncompressed XISF images. To measure codecs separately from tiny-file opening overhead, generate independent cases:

python tools/benchmarks/generate.py --output artifacts/load-benchmarks/synthetic-images
python tools/benchmarks/load.py --directory artifacts/load-benchmarks/synthetic-images --astroview tools/AstroView.Performance/bin/Release/net10.0/AstroView.Performance.dll --output artifacts/load-benchmarks/synthetic-run

Default data: a 4096 x 4096 UInt16 monochrome image (32 MiB) and a 2048 x 2048 RGB Float32 image (48 MiB). Seeded gradients plus noise produce identical decoded values for each codec. Python xisf writes uncompressed, zlib, LZ4, LZ4HC and Zstandard files, with byte shuffling for compression. Astropy writes matching uncompressed FITS images with declared checksums. XISF files have no block digests, so this set also compares decoding without the readers' digest-policy difference. The writer can decline ineffective compression; the manifest and reports record the codec actually selected. FITS retains its standard unsigned offset encoding.

The generated manifest.json records producer versions, seed, file hashes and canonical physical-pixel hashes. Pixel values are reproducible with the pinned NumPy version; creation timestamps can change file bytes between generations. Use --size 64 for a quick functional check. Generation requires a fresh directory and never imports AstroView. Generated images and full local results stay outside Git; aggregate results can be shared independently of the photo corpus.

Publish aggregate results safely

Keep full reports under ignored artifacts/. Export aggregate evidence with tools/benchmarks/summarize.py --dataset 'Label=path/to/report.json' --output path/to/aggregate.json. Repeating a label combines disjoint stages while rejecting duplicate measurements, changed source bytes and different machines/packages. Photo filenames, paths, individual hashes and error text are omitted. Publication rejects incomplete runs and unresolved pixel mismatches.

The recorded guide tables are generated from the checked-in aggregate JSON. CI verifies them using:

python tools/benchmarks/summarize.py --output docs/benchmark-results/2026-11-01.json --markdown docs/benchmarks.md --check

Omit --check to synchronize the tables after replacing the recorded evidence. Update the surrounding interpretation when a new run changes the conclusions.
