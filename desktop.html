AstroView

Desktop development guide

For task-oriented application instructions, read the desktop user manual. This page covers development and the connection between workspaces and Core features.

AstroView is an Avalonia 12.1 desktop application targeting .NET 10. Its scientific operations run through AstroView.Core; the library has no Avalonia dependency. The app starts with an original synthetic reference scene, so it works without downloads, internet access or the large local photograph corpus.

dotnet restore AstroView.sln --locked-mode
dotnet run --project src/AstroView.Desktop -c Release

Open FITS, XISF or distributed XISH headers with Open images, drag files onto the window, or pass paths after -- on the command line. Detection reads the content rather than trusting extensions. The left sidebar selects documents and their image/HDU entries. Close documents to release retained pixels and previews.

The reference scene contains synthetic Float32 RGB emission data, a UInt16 gradient, a scientific cube, a complex wave, a native linear astrometric solution, and a typed reference-star catalog. Generated data are demonstration data, not independent interoperability evidence and do not close AV-002's remaining gaps.

The feature guide records the UI entry point and scope for each capability. Core features still on the roadmap are labelled unavailable. Complex and scientific cube samples remain inspectable; Core currently has no general magnitude/phase or cube-plane bitmap renderer. FITS table editing and broader WCS evaluation remain Core roadmap work. CFA and ICC metadata are inspectable/preservable; this does not imply debayering or a full ICC colour-management engine.

Scientific values, editing and output

Display stretching changes previews only. Histograms count all samples in one channel; statistics are estimates controlled by the sample limit. Their limits do not make the underlying full-image decoding a streaming operation. Large documents can retain substantial memory. Region access currently decodes full blocks. Integer statistics/Float64 region views can round very large integers; the stored-sample inspector prints UInt64 directly with exact integer text.

Metadata and table edits apply to the in-memory document. Export a copy to persist them; active source filenames are guarded against replacement. Native copies use Core's document-preserving writer. Re-encoding materializes editable content and does not retain the original signature. Isolating an image copies its image metadata; document-level content stays in the original document. Conversion losses are rejected unless the user explicitly allows them. Inspect the fidelity report before accepting omissions; unrepresentable pixel types fail explicitly.

Distributed output requires a new header name and creates a unique sibling block file. It is a two-file operation, not an atomic transaction; the app removes its new partial outputs on failure. The signed-copy demonstration generates an ephemeral RSA key, signs a copy and discards the private key. Embedded-key verification demonstrates integrity and does not authenticate an identity.

The table JSON editor's example shows its schema. It supports scalar String, Boolean, TimePoint and the ordinary signed/unsigned integer and real types, plus integer/real vectors and rectangular matrices. It bounds interactive input to 1,000 rows, 32 fields and 4,096 elements per array cell. Core serializes the cells; the editor inserts embedded table XML without copying the original image blocks. Other types remain accessible through full XISF XML or the native Core API.

Network resources, general external paths and directory traversal default off. Header-relative sibling blocks default on. Reader policy changes apply to newly opened documents. XSD loading disables DTD and network resolution. Long work runs off the UI thread; cancellation is cooperative and some codec/CPU operations finish their current block before returning. Publication operations disable cancellation in the UI while committing output.

Development and verification

dotnet build AstroView.sln -c Release --no-restore
dotnet test AstroView.sln -c Release --no-build
dotnet publish src/AstroView.Desktop -c Release --no-build -o artifacts/desktop-app

The desktop workflow tests use Avalonia's headless platform with real Skia drawing and Inter fonts. They exercise native file loading, UI state, typed generation, metadata/table edits, exact samples, coordinates, validation, conversion loss rejection, re-encoding, distributed files, signatures and PNG output. Every workspace is rendered to tests/AstroView.Desktop.Tests/bin/Release/net10.0/ui-artifacts. Set ASTROVIEW_UI_ARTIFACTS to override that path. The headless dispatcher uses an explicit async result overload so tests await their complete workflow.

CI runs both library and desktop tests on Windows, Linux and macOS. It uploads test results, the synthetic workspace screenshots and framework-dependent desktop publish directories. These builds require the .NET 10 runtime and the platform's ordinary Avalonia native prerequisites. Run dotnet AstroView.dll from a downloaded publish directory; no installer, signing/notarization or file association is supplied.

Tagged GitHub releases provide a separate desktop ZIP with self-contained single-file executables. These include .NET and can run by themselves. Each is checked in isolation with --self-test before publication.

The opt-in local desktop test renders the user's Bubble FITS and Carina Ha XISF files from C:\Code\AstroExamples, checks original hashes and keeps screenshots local under local-ui-artifacts in the test output. These photographs and captures are excluded from Git and CI uploads:

dotnet test tests/AstroView.Desktop.Tests -c Release `
  --environment ASTROVIEW_DESKTOP_EXAMPLES=C:/Code/AstroExamples `
  --filter FullyQualifiedName~LocalDesktopTests

Models adapt native documents for display; Services handle file dialogs, loading, table editing and export; ViewModels group operations by workspace; Views contain XAML; Controls draw the image viewport and histogram. Add a Core feature to the feature guide, its relevant workspace, a workflow test and this coverage table as it becomes available. Keep format/astronomy algorithms in Core.

Avalonia's build-time telemetry can be disabled with AVALONIA_TELEMETRY_OPTOUT=1 (already set in CI). Desktop dependency notices ship beside the app; they do not add GUI dependencies or GUI binaries to the Core NuGet.
