Resource policy and performance

Understand the memory model first

Current readers and operations are not a general streaming or memory-mapped processing API. FITS loads retain materialized HDU payloads. XISF path loads can defer blocks, but a pixel read/decompression materializes a complete block. Region extraction and sampled statistics do not make that block decode partial.

For a 10,000 × 10,000 single-channel image, the pixel buffer alone is roughly 200 MB as UInt16, 400 MB as Float32 or 800 MB as double. RGB multiplies scientific sample storage by three; a BGRA preview adds roughly 400 MB. Compressed input, temporary codec buffers, typed copies, metadata and application state add more. Use these estimates for planning rather than interpreting them as peak-memory guarantees.

Budgets protect different stages. Raising MaximumDataBlockSize does not raise every other limit or ensure sufficient memory. Some highly compressible but valid data can exceed the ratio limit; change a limit only with an understood workload.

ExternalResourceResolver lets an application provide resource streams under its own policy. Treat URI authorization, credentials, allowed hosts/paths, timeouts and response-size enforcement as application responsibilities as well as honoring Core's access flags. A custom resolver is not permission to ignore the reader's resource policy. Resolver streams have the ownership contract documented on that API.

Table element budgets account for array elements, characters and bits, including repeated heap references. A small number of table cells can still expand into a large number of values. The total decoded byte setting describes retained raw HDU payloads; it is not a process-wide cap on every allocation.

Async and cancellation

public static async Task AsyncIo(string directory)
{
    using var cancellation = new CancellationTokenSource(TimeSpan.FromSeconds(30));
    var document = await XisfReader.LoadAsync(Path.Combine(directory, "image.xisf"),
        cancellationToken: cancellation.Token);
    await XisfWriter.WriteAsync(Path.Combine(directory, "async-copy.xisf"), document,
        cancellationToken: cancellation.Token);
    // Await completion before changing editable objects or releasing source files.
}

The API includes worker-thread wrappers around synchronous parsing/codec work. Async does not imply incremental decoding, constant memory or cancellation inside every compression operation. Some work completes its current block before observing cancellation. Await completion before editing input objects or disposing streams your application supplied.

Path writes stage single-file output and check cancellation around publication. Caller streams can contain partial data after errors/cancellation. Distributed XISF involves multiple paths and needs application-level cleanup/publication coordination.

Practical integration choices

  • Keep native documents and defer typed sample copies until needed.
  • Request a matching integer type for exact work instead of normalizing every image to double immediately.
  • Avoid repeatedly asking for the same full decoded block, typed copy and preview during a single operation. Cache owned results at your application layer when that tradeoff is appropriate, then release them when documents close.
  • Bound concurrent decodes by available memory, not just processor count.
  • Separate background work from UI updates and provide progress at meaningful operation boundaries rather than inventing per-pixel progress.
  • Benchmark with your real sample types, channel counts, codecs and file layouts. A synthetic compression ratio or one codec benchmark does not predict all astronomical workloads.

See testing for local corpus tests and the repository's performance tool. Broader streaming, shared typed access and compressed FITS are recorded in the roadmap.
