Converting FITS and XISF

Preservation, transformation and omission

Native document copying and cross-format conversion solve different problems. Use the native writer when retaining unknown extensions or format-specific structure matters. Use FitsConverter when you need a different image model, then inspect its findings before writing the destination.

ConversionResult<T> contains Value, Findings and HasLosses. ConversionFinding exposes Code, Effect and Message. Effects distinguish preserved content, transformed content and omitted content. HasLosses tracks omissions; a transformation can still be scientifically important even when that Boolean is false. Read the findings rather than reducing them to one flag.

Default loss policy

The default policy is ConversionLossPolicy.Reject. A conversion with reported omissions throws ConversionLossException, which contains the findings. Use that exception to present a review step. Set Allow only when your application or user has accepted the omission policy.

public static void Conversion(string directory)
{
    var source = XisfReader.Load(Path.Combine(directory, "catalog.xisf"));
    try
    {
        _ = FitsConverter.ConvertToFits(source); // Rejects omissions by default.
        throw new InvalidOperationException("Expected metadata loss to require a decision.");
    }
    catch (ConversionLossException error)
    {
        foreach (var finding in error.Findings)
            Console.WriteLine($"{finding.Effect}: {finding.Code}: {finding.Message}");
    }
    // Continue only after your application/user accepts the reported omissions.
    var accepted = FitsConverter.ConvertToFits(source, ConversionLossPolicy.Allow);
    FitsWriter.Write(Path.Combine(directory, "converted.fits"), accepted.Value);
}

Allowing omissions does not force an impossible pixel conversion. Unsupported complex image storage or an exactness constraint can still cause a failure. Do not catch every exception and retry with a lossy floating-point image unless that is a separately designed feature of your application.

FITS to XISF

ConvertToXisf(fitsDocument, options) returns editable images and findings. FitsConversionOptions.AxisInterpretation defaults to PreserveDimensions. Choose RgbOrRgba only for files whose third axis really represents color. IncludeStructuralKeywords controls whether structural FITS cards are also retained as XISF FITS keywords.

FITS scaling/blank handling can transform stored integer data into physical floating-point samples. Conventional unsigned storage has dedicated typed paths. See FITS exact values before converting Int64 or UInt64 data through double precision.

FITS table conversion can report omission of native table storage, units, scaling or extension details; array cells can be flattened to text. Unknown extensions may be omitted. Treat the result as a conversion of supported content, not a complete archive of the original FITS HDUs.

XISF to FITS

Prefer the XisfDocument conversion overload when reviewing an entire source document: it reports document-level as well as image-level omissions. Passing only selected image data cannot report content you have already left behind.

Native XISF properties, astrometric solutions, global metadata, tables, color objects and application extensions may not have an equivalent FITS representation in this converter. Even if FITS has a related convention in principle, this implementation must explicitly support that mapping before it can preserve it.

For selected-image export, first decide whether to retain or intentionally omit global properties and tables. Copying Images[0] into a new document does not automatically bring the original document's global content with it.

Verify a conversion

  1. Review every omitted and transformed finding.
  2. Write to a new path with the chosen checksum policy.
  3. Reopen the output using your intended reader options.
  4. Compare dimensions, channel interpretation, sample types and values at the precision required by your application.
  5. Verify expected metadata and tables explicitly; pixel equality alone is not a document-fidelity check.
  6. Use independent readers/reference data for interoperability claims.

The repository's interoperability evidence records independent tools, fixtures and remaining gaps. Self-generated examples and forward/backward conversions are useful regression checks but are not a substitute for independent validation.
