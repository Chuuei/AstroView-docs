AstroView

GitHub releases

The Release Actions workflow creates a GitHub Release when a matching version tag is pushed. It adds two downloads:

Asset Contents
AstroView.Desktop-<version>.zip One self-contained executable per platform: Windows x64, Linux x64 (glibc), macOS Apple silicon. Includes .NET and native rendering libraries.
AstroView.Core-<version>.zip Core DLL, required compression/cryptography DLLs, XML documentation, an MSBuild reference file and the normal Core NuGet package. No desktop assemblies.

GitHub also supplies its standard source-code ZIP and tarball automatically. Both AstroView archives contain notices, usage instructions and a manifest with the version and each file's SHA-256. Release notes include both archive hashes.

Single-file .NET applications are specific to an OS and CPU architecture; a single executable cannot serve all platforms. Each desktop executable can run by itself. Native libraries extract to .NET's temporary bundle cache at launch. Normal OS prerequisites still apply. The archive README explains execution permissions, supported targets and the unsigned macOS executable (no .app or notarization). Executables are not trimmed, preserving Avalonia and XML signature reflection.

.NET does not provide single-file publishing for a reusable managed class library. The Core archive therefore includes its required managed dependencies separately. Import its AstroView.Core.props in a .NET 10 project to reference the DLLs, or use its .nupkg through a local NuGet source. The package restores its dependencies normally; the direct DLL option works without a package restore for Core. Follow the archive README when cross-publishing a consumer with an explicit runtime ID.

Publish a release

  1. Update eng/Versions.props and CHANGELOG.md; commit and push the changes.
  2. Create a matching tag, for example git tag v0.2.0 or git tag v0.2.0-rc.1.
  3. Push that tag: git push origin v0.2.0 (use the actual tag).
  4. Watch Release in Actions. After all checks pass, the workflow creates the release, uploads both assets and publishes it. Prerelease tags automatically create GitHub prereleases.

The workflow validates tags against the version policy. Publication uses the built-in GITHUB_TOKEN with contents: write only in the final job. No personal token or package-registry secret is needed. It requires the remote tag to exist and never overwrites an existing release. The GitHub CLI stages the release as a draft while uploading, so a failed upload cannot publish a partial release. If uploading fails, inspect/delete the incomplete draft before rerunning. Published versions should receive a new version/tag for corrections.

This workflow does not publish to nuget.org. Creating a version commit or manually running the workflow does not create a GitHub Release.

Validate without publishing

Choose Actions → Release → Run workflow on the desired branch. This runs the same checks and produces a release-downloads workflow artifact containing the two ZIPs and release notes, but skips publication. Branch runs use the normal <version>-ci.<run>.<attempt> version.

Every release run gates assembly/publication on:

  • The existing Windows/Linux/macOS build, Core and headless desktop tests, version checks, NuGet packing and independent FITS/XISF reference-reader checks.
  • Native self-contained publishing with locked runtime-specific dependencies.
  • Running each executable with --self-test in a directory containing only that executable: all XISF codecs, FITS samples, XML/PKCS signatures, Core rendering and native Skia PNG encoding/decoding. This check does not require a display; workspace behavior is covered by the separate headless tests.
  • Compiling/publishing/running an independent .NET consumer of each extracted Core archive, with no Core ProjectReference, no PackageReferences and cleared package sources; cross-publishing also verifies the target's cryptography DLL is selected.
  • Archive contract tests, complete payloads, executable permissions, matching versions and SHA-256 manifests.

Local packaging

Use the .NET 10 SDK, Python 3.10+ and PowerShell on the target OS:

./eng/Build-Release.ps1 -Runtime win-x64 -Version 0.2.0-dev -Output artifacts/release-local

Use linux-x64 or osx-arm64 on those platforms. Output must be a new directory. This script runs native installation checks and must run on the specified target platform. It builds the desktop payload and Core archive; CI combines the three desktop payloads into the final desktop ZIP using eng/release_archives.py.

The ordinary project lock files remain platform-independent. Single-file release graphs have packages.release.<runtime>.lock.json in Core and Desktop. When changing packages or the SDK/runtime patch used for releases, intentionally regenerate each target graph and commit its updated locks:

dotnet restore src/AstroView.Desktop -p:RuntimeIdentifier=win-x64 `
  -p:PublishRuntimeIdentifier=win-x64 `
  -p:AstroViewReleaseRuntime=win-x64 -p:PublishSingleFile=true `
  -p:SelfContained=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:PublishTrimmed=false --force-evaluate

Repeat for the other two RIDs. Do not disable locked restore in the release job. Set both runtime properties to the same RID: during restore, .NET 10 otherwise can also infer the host's publish runtime when single-file publishing is enabled.
